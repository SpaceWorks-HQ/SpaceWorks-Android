# Payments and issued documents

Home dues and Profile open the selected makerspace's payments. Amounts, currencies, due states, settlement metadata and refunds come from the generated payment-list operation. Unknown statuses cannot enable checkout. A payment link requires a successful fresh list read containing its actual ID; a refused or superseded response cannot open a cached charge.

The current owner contract returns Stripe mobile-intent configuration. The Activity registers Stripe PaymentSheet and the approved Razorpay adapter before STARTED, but only the documented server-selected Stripe intent is launchable in production. No Razorpay API shape, order or rail selector is invented. A later server contract can supply its adapter inputs. Owner provider keys, merchant setup and live native sessions remain required.

Checkout rechecks the charge before requesting an intent. SDK credentials remain ephemeral and redacted; no amount is calculated or changed locally. Every SDK closure, including cancellation, failure and interruption, requires an authoritative payment-list refresh. A submitted SDK result is never displayed as paid. Bounded polling can reach `paid_online`, `paid_offline` or another actual status; an unresolved result stays pending with an explicit status check. An offline or throttled callback remains blocked until its refresh succeeds. Restored opaque callback references cannot identify a charge or transfer an old outcome to another account.

Sign-out removes protected identity and private holders immediately, then uses the captured old grant and recorded push scopes for cleanup before token teardown. Checkout launch also requires the same account installation, selected makerspace and an available auth host. Maker changes invalidate private payment reads, intents and previews before publishing the new selection.

Issued receipts and credit notes use generated page arguments and exact validated next links. The short-lived PDF grant is parsed only for the documented same-origin path, actual document ID and token. The generated PDF download explicitly requires JWT authentication, unlike the separate public account-export archive. Installation ownership is checked across grant creation and download; an account replacement cannot issue the second signed request. Streaming enforces PDF MIME, signature and a 25 MiB cap, with thread-safe call cancellation.

Native PdfRenderer previews use opaque files in `cache/native-documents`. Save uses the system document picker. Share grants only the selected file through the non-exported FileProvider. A recipient receives a fifteen-minute file lease; close, scope changes and logout otherwise remove the preview. Cold launch removes only recognized document files older than a day. Signed URLs, credentials and document bodies are not logged or persisted as navigation state.

DEBUG-only demo payments are isolated in memory. The preview checkout exercises paid, delayed, cancelled, failed, offline and unavailable outcomes without opening an SDK or moving money. Synthetic receipt PDFs are clearly marked as samples. Release contains no sample payment gateway. Production API coverage, state/ownership/callback tests and native phone/tablet journeys accompany this phase; live payment success is not claimed while owner backend/provider setup is deferred.
